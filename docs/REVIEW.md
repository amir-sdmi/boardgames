# Code review — 19 September 2026

## Assessment

The project is a working prototype with a clearer authentication boundary and useful domain types. It is **not yet production-ready or “perfect.”** The highest risks are multiplayer authorization, concurrent writes, and several reproducible game defects. Those game behaviors were deliberately preserved because this review was authorized to improve structure, not change the rules or game logic.

This was a source review of the routes, authentication/setup, room service, game context, every game action, initialization, card/trade helpers, game UI, shared UI, configuration, and existing tests. Static assets were reviewed as imports and presentation dependencies, not for artwork quality. Firebase production configuration, deployed rules, real multi-browser gameplay, and hosting were unavailable and are not certified by this review.

## Improvements made in this review

- Centralized the homepage/lobby background without changing the game layout.
- Centralized server-side page protection and auth-page redirect behavior; each protected page still checks a real database session.
- Consolidated game button markup with accept/reject variants while keeping compatibility imports.
- Replaced six repeated purchase callback signatures with one UI type.
- Removed the duplicate field-image array while preserving the same image order.
- Made the price legend read the existing `PRICES` values. The cards legend now correctly shows 1; the charged price is unchanged.
- Removed abandoned commented UI and an accidentally committed terminal transcript.
- Added characterization tests, an explicit testing directory split, and a CI workflow.
- Replaced floating `latest` development dependency declarations with version ranges backed by the lockfile.

See [completed work](COMPLETED.md), [remaining work](REMAINING_WORK.md), and [architecture](ARCHITECTURE.md).

## Verification and limits

The new unit tests exercise all game-action entry points using an in-memory persistence boundary, room operations through a mocked Firestore SDK, initialization for 1–7 players, harvest thresholds, purchases, planting, trading, and safe auth return URLs. Known-defect tests are named as such; a passing suite does not mean these defects are desirable or fixed.

Playwright tests run the real Next.js production server with a separate SQLite database. They verify account creation, cookies, login/logout/revocation/expiry, route protection, password rejection, origin checks, and rate limits. They do **not** exercise real Firebase multiplayer or prove concurrency safety. CI was authored locally; a hosted GitHub Actions run will occur only after the changes are pushed.
